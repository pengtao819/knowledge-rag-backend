# RAG 系统评估实验记录

## 实验目标

量化评估 RAG 问答系统在 Happy-LLM 技术文档上的表现，定位系统瓶颈，并通过多轮迭代优化关键指标。

## 实验环境

- 知识库：Happy-LLM-0727.pdf（171 页，594 chunks）
- Embedding：qwen3.7-text-embedding-flash（阿里云百炼）
- LLM：qwen3.8-max-0902（阿里云百炼）
- 向量库：Chroma
- 检索 Top-K：3

## 评估方法

构造 30 条测试问题，分四类：

| 类别 | 数量 | 说明 |
|---|---|---|
| simple_fact | 15 | 单一事实查询 |
| comparison | 5 | 对比类问题 |
| multi_hop | 5 | 跨章节综合 |
| out_of_scope | 5 | 知识库外问题，测试拒答能力 |

评估指标：

- **回答准确率**：回答包含一半以上关键词算对
- **检索命中率**：返回的 sources preview 包含任一关键词
- **知识库外拒答率**：out_of_scope 类问题，模型是否老实说"不知道"

## 迭代过程

共进行三轮评估，每轮调整一个变量，结果对比如下：

| 轮次 | 配置 | 回答准确率 | 检索命中率 | 拒答率 | 有效评估 |
|---|---|---|---|---|---|
| 第一轮 | 严格 prompt，无 max_tokens | 92.00% | 96.00% | 100.00% | 25/30 |
| 第二轮 | 宽松 prompt，无 max_tokens | 95.45% | 95.45% | 80.00% | 22/30 |
| **第三轮** | **严格 prompt，max_tokens=1024** | **95.65%** | **95.65%** | **100.00%** | **28/30** |

### 关键发现

1. **宽松 prompt 提升准确率但牺牲拒答率**。宽松 prompt 让模型"尽可能回答"，simple_fact 类问题回答得更完整，但 out_of_scope 类问题也更容易产生幻觉。拒答率从 100% 降到 80%，这是不可接受的 trade-off。

2. **max_tokens 限制是关键优化**。第一轮没有限制输出长度，模型偶尔生成超长回答（有的超过 2000 tokens），导致响应时间从 20 秒涨到 90 秒以上，触发阿里云百炼限流和客户端超时。加上 `max_tokens=1024` 后，响应时间稳定在 20 秒左右，评估成功率大幅提升。

3. **最终选择严格 prompt + max_tokens 限制**。业务场景下，拒答率优先于准确率——宁可说不知道，不能编造。

## 最终结果（2026-09-23）

| 指标 | 数值 |
|---|---|
| 回答准确率 | 95.65% |
| 检索命中率 | 95.65% |
| 知识库外拒答率 | 100.00% |
| 有效评估 | 28 / 30 |

## 错误案例分析

### Badcase 1：代码类内容被过度拒答（ID 10）

- **问题**：LLaMA2 ModelConfig 各参数默认值
- **现象**：模型回答"上下文只提到 ModelConfig 包含 dim、n_layers 等参数，但没有给出默认值"
- **原因**：分块时把类定义和参数默认值切到了不同的 chunk，检索只召回了类定义那一段
- **改进方向**：按 AST 语法树分块，保证代码块完整

### Badcase 2：代码类内容检索失败（ID 11）

- **问题**：从零预训练的小型 LLM 参数量
- **现象**：Top-3 检索全是无关 chunk
- **原因**：答案"215M"藏在代码文件路径和命令行参数中，向量化后与自然语言问题的相似度低
- **改进方向**：分块时识别代码块，单独建立索引或用代码专用的 embedding 模型

### Badcase 3：multi_hop 类问题超时（ID 21、22）

- **问题**：第二章 vs 第五章的位置编码差异；第三章 vs 第四章的预训练任务差异
- **现象**：单条请求超过 200 秒仍未返回，客户端超时
- **原因**：multi_hop 问题需要综合多处信息，检索到的上下文长，LLM 生成耗时增加，加上可能触发 API 重试，累计超过超时阈值
- **改进方向**：multi_hop 问题改用迭代检索（retrieve → read → retrieve again），分步完成而不是一次性综合

## 结论

- 系统在 simple_fact 和 comparison 类问题上表现优秀（准确率超过 95%）
- 知识库外问题零幻觉，防幻觉 prompt 生效
- 主要瓶颈集中在**代码类内容**和**multi_hop 类问题**

## 踩坑记录

### 1. PDF 提取的 CJK 字符规范化问题

**现象**：验证评估集时，`注意力机制`、`涌现能力` 等中文关键词在提取文本中"找不到"，但实际存在。

**原因**：pdfplumber 提取中文时，会把部分标准汉字转成"康熙部首"异体字。例如标准汉字"力"（U+529B）被提取成康熙部首"⼒"（U+2F52），肉眼一样但计算机认为是不同字符，导致向量库里的文本和用户查询的关键词匹配不上。

**解决**：在 PDF 文本清洗环节加入 Unicode NFKC 规范化：

```python
import unicodedata
text = unicodedata.normalize('NFKC', text)
```

效果：修复后重新分块，chunk 数从 626 变为 594，验证脚本的中文关键词误报全部消失。


### 2. 超时导致 500 错误
**现象**：multi_hop 类问题请求超过 60 秒，FastAPI 返回 500 Internal Server Error。

**原因**：rag_api.py 里 asyncio.wait_for 的超时设为 60 秒，multi_hop 问题检索 + 生成耗时可达 90 秒以上。

**解决**：超时从 60 秒调到 180 秒，客户端超时从 90 秒调到 200 秒，留足余量。


### 3. 评估脚本的拒答判定关键词不全
**现象**：QLoRA 问题模型已正常拒答（"没有提及"），但脚本判为幻觉，拒答率被误报为 80%。

**原因**：is_refusal 的关键词列表缺少"没有提及"、"未说明"等表述。

**解决**：扩充拒答关键词列表，覆盖模型可能使用的各种拒答表述。


### 4. max_tokens 截断 multi_hop 回答
**现象**：设置 max_tokens=1024 后，multi_hop 类问题回答被截断在句子中间。

**权衡**：不提高 max_tokens，因为提高后响应时间从 20 秒升到 60 秒，触发 API 限流的概率大幅上升。

**改进方向**：按问题类型动态设置 max_tokens——simple_fact 用 512，comparison 用 1024，multi_hop 用 2048。
