# RAG 系统评估实验记录

## 实验目标

量化评估 RAG 问答系统在 Happy-LLM 技术文档上的表现，定位系统瓶颈。

## 实验环境

- 知识库：Happy-LLM-0727.pdf（171 页，594 chunks）
- Embedding：qwen3.7-text-embedding-flash（阿里云百炼）
- LLM：qwen3.8-max-0902（阿里云百炼）
- 向量库：Chroma
- 检索 Top-K：3

## 评估方法

构造 30 条测试问题，分四类：

| 类别 | 数量 | 说明 |
|---|---|---|
| simple_fact | 15 | 单一事实查询 |
| comparison | 5 | 对比类问题 |
| multi_hop | 5 | 跨章节综合 |
| out_of_scope | 5 | 知识库外问题，测试拒答能力 |

评估指标：
- 回答准确率：回答包含一半以上关键词算对
- 检索命中率：返回的 sources preview 包含任一关键词
- 知识库外拒答率：out_of_scope 类问题，模型是否老实说"不知道"

## 评估结果（2026-09-23）

| 指标 | 数值 |
|---|---|
| 回答准确率 | 92.00% |
| 检索命中率 | 96.00% |
| 知识库外拒答率 | 100.00% |
| 错误案例 | 3 / 30 |

## 错误案例分析

### Badcase 1：代码类内容被过度拒答（ID 10）

- 问题：LLaMA2 ModelConfig 各参数默认值
- 现象：模型回答"根据当前知识库无法确定"
- 原因：检索命中了代码片段，但 prompt 的拒答条件过严，模型不敢基于代码片段回答
- 改进方向：放松 prompt 拒答条件

### Badcase 2：代码块检索失败（ID 11）

- 问题：从零预训练的小型 LLM 参数量
- 现象：Top-3 检索全是无关 chunk
- 原因：答案在代码文件路径和注释中，向量化后与自然语言问题的相似度低
- 改进方向：分块时识别代码块，单独建索引或用不同的 embedding 策略

### Badcase 3：multi_hop 检索不完整（ID 21）

- 问题：第二章 vs 第五章的位置编码差异
- 现象：模型拒答
- 原因：Top-3 只召回了一边的信息，模型判断上下文不完整
- 改进方向：multi_hop 问题改用迭代检索（retrieve → read → retrieve again）

## 结论

- 系统在 simple_fact 和 comparison 类问题上表现优秀
- 主要瓶颈在代码类内容检索和 multi_hop 检索
- 知识库外问题零幻觉，防幻觉 prompt 生效

## 踩坑记录

### PDF 提取的 CJK 字符规范化问题

**现象**：验证评估集时，`注意力机制`、`涌现能力`等中文关键词在提取文本中"找不到"，但实际存在。

**原因**：pdfplumber 提取中文时，会把部分标准汉字转成"康熙部首"异体字。例如标准汉字"力"（U+529B）被提取成康熙部首"⼒"（U+2F52），肉眼一样但计算机认为是不同字符。这导致向量库里的文本和用户查询的关键词匹配不上。

**解决**：在 PDF 文本清洗环节加入 Unicode NFKC 规范化：

```python
import unicodedata
text = unicodedata.normalize('NFKC', text)
